# 体锻室预约系统 — 项目计划文档

> 项目性质：单人实验项目 | 阶段：未启动 | 负责人：金锋

# 第一部分：产品需求文档（PRD）

## 1. 项目背景与目标

### 1.1 背景
体锻室（体能锻炼测试室）是供员工/成员进行体能测试的专用场所。当前缺乏预约管理机制，可能出现人员扎堆、测试设备闲置或争抢的情况。需要一个轻量级的预约系统，确保「预约通过 → 核销签到 → 进入测试」的闭环。

### 1.2 目标
- **核心目标**：实现体锻室的预约与核销管理，确保只有预约成功的人才能进入测试。
- **MVP 范围**：预约、取消、签到核销、管理端时段设置。
- **非目标（本期不做）**：支付、消息推送、数据大屏、设备管理。

## 2. 用户角色

| 角色 | 说明 | 核心需求 |
|------|------|----------|
| 普通用户 | 需要预约体锻室的成员 | 查看时段、预约、取消预约、签到 |
| 管理员 | 体锻室管理人员 | 设置可预约时段、查看预约情况、核销签到 |

> MVP 阶段，管理员可为系统内置账号，暂不开放注册审批流程。

## 3. 功能需求

### 3.1 用户端

#### F1 — 用户登录
- 支持账号密码登录
- 登录后获取 token，后续请求携带 token

#### F2 — 查看可预约时段
- 按日期展示可预约时段列表
- 每个时段显示：时间范围、剩余名额、状态（可预约/已满/已过期）
- 默认展示未来 7 天的时段

#### F3 — 预约时段
- 用户选择一个可预约时段，点击预约
- 每个用户同一时段只能预约一次
- 预约成功后扣减时段名额
- 名额已满时不可预约

#### F4 — 我的预约
- 查看自己的预约列表，按时间倒序
- 展示预约状态：待签到、已签到、已取消、已过期
- 未开始的预约可取消

#### F5 — 取消预约
- 预约开始时间之前可取消
- 取消后释放时段名额
- 已过期/已签到的不允许取消

#### F6 — 签到核销
- 用户到达体锻室后签到
- 签到窗口：预约时段开始前 15 分钟 ~ 结束后 15 分钟
- 签到后状态变为「已签到」，方可进入测试

### 3.2 管理端

#### F7 — 时段管理
- 创建可预约时段：日期 + 开始时间 + 结束时间 + 容量（人数上限）
- 支持批量创建（如：未来一周每天 9:00-10:00，容量 5 人）
- 删除未开始的时段
- 修改时段容量

#### F8 — 预约管理
- 查看所有预约记录，支持按日期/状态筛选
- 手动核销签到（用户忘记签到时的兜底）
- 手动取消预约

## 4. 业务流程

### 4.1 预约主流程
```
管理员创建时段 → 用户浏览时段 → 用户预约 → 
预约时间到达 → 用户签到 → 进入体锻室测试
```

### 4.2 状态流转
```
预约创建 → [待签到]
    ↓ 用户取消
  [已取消]
    ↓ 用户签到
  [已签到]
    ↓ 超时未签到
  [已过期]
```

## 5. 非功能需求

| 类型 | 要求 |
|------|------|
| 并发 | MVP 阶段支持 50 用户同时访问 |
| 数据一致性 | 预约名额扣减需保证并发安全（加锁） |
| 响应时间 | 页面加载 < 2s，接口响应 < 500ms |
| 安全 | 密码加密存储，接口鉴权 |

# 第二部分：架构及接口设计文档

## 1. 技术选型

| 层级 | 技术 | 理由 |
|------|------|------|
| 前端 | React 18 + Ant Design 5 | 组件丰富，单人开发效率高 |
| 后端 | Node.js + Express | JS 全栈，降低上下文切换成本 |
| 数据库 | SQLite（MVP） | 零配置，单人项目够用，后续可迁 PostgreSQL |
| 鉴权 | JWT（jsonwebtoken） | 无状态，实现简单 |
| 密码加密 | bcrypt | 行业标准 |

> **备选方案**：如果后续需要小程序端，后端保持不变，前端换 Taro/uni-app 即可。

## 2. 系统架构

```
┌─────────────┐     HTTP/JSON      ┌──────────────┐     SQL      ┌──────────┐
│   React Web  │ ◄────────────────► │  Express API  │ ◄──────────► │  SQLite  │
│   (Nginx)    │     JWT Auth       │   (Node.js)   │              │          │
└─────────────┘                     └──────────────┘              └──────────┘
```

- 前后端分离，前端静态资源由 Nginx 托管
- 后端 RESTful API，JSON 格式交互
- JWT 无状态鉴权，登录后 token 有效期 24h

## 3. 数据库设计

### 3.1 ER 图概要

```
users  1 ──── N  reservations  N ──── 1  time_slots
                      │
                      N
                      │
                      1
                  check_ins
```

### 3.2 表结构

**users（用户表）**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增主键 |
| username | VARCHAR(50) UNIQUE | 用户名 |
| password_hash | VARCHAR(255) | bcrypt 加密 |
| real_name | VARCHAR(50) | 真实姓名 |
| role | VARCHAR(20) | user / admin |
| created_at | DATETIME | 创建时间 |

**time_slots（时段表）**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增主键 |
| date | DATE | 日期 |
| start_time | TIME | 开始时间 |
| end_time | TIME | 结束时间 |
| capacity | INTEGER | 总名额 |
| reserved | INTEGER DEFAULT 0 | 已预约数 |
| status | VARCHAR(20) | active / cancelled |
| created_at | DATETIME | 创建时间 |

**reservations（预约表）**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增主键 |
| user_id | INTEGER FK | 用户 ID |
| slot_id | INTEGER FK | 时段 ID |
| status | VARCHAR(20) | pending / checked_in / cancelled / expired |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 更新时间 |

> 唯一约束：UNIQUE(user_id, slot_id)，防止同一用户重复预约同一时段。

**check_ins（签到表）**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增主键 |
| reservation_id | INTEGER FK UNIQUE | 预约 ID |
| check_in_time | DATETIME | 签到时间 |
| checked_by | VARCHAR(50) | 签到方式：self / admin |

### 3.3 状态枚举

**预约状态（reservations.status）**
- `pending`：已预约，待签到
- `checked_in`：已签到
- `cancelled`：已取消
- `expired`：超时未签到

**时段状态（time_slots.status）**
- `active`：正常可用
- `cancelled`：管理员取消

## 4. API 接口设计

> Base URL: `/api/v1`
> 鉴权方式：Header `Authorization: Bearer <token>`（除登录/注册外均需）

### 4.1 认证模块

#### POST /auth/register
注册新用户
```
Request:  { "username": "zhangsan", "password": "xxx", "real_name": "张三" }
Response: { "code": 0, "data": { "id": 1, "username": "zhangsan" } }
```

#### POST /auth/login
用户登录
```
Request:  { "username": "zhangsan", "password": "xxx" }
Response: { "code": 0, "data": { "token": "eyJ...", "user": { "id": 1, "role": "user" } } }
```

### 4.2 时段模块

#### GET /slots
查询可预约时段
```
Query:    ?date=2026-08-05&days=7
Response: { "code": 0, "data": [ { "id": 1, "date": "2026-08-05", "start_time": "09:00",
             "end_time": "10:00", "capacity": 5, "reserved": 2, "available": 3 } ] }
```
> `days` 默认 7，表示从 `date` 起查询几天。

#### POST /slots
管理员创建时段（需 admin 角色）
```
Request:  { "date": "2026-08-05", "start_time": "09:00", "end_time": "10:00", "capacity": 5 }
Response: { "code": 0, "data": { "id": 1 } }
```

#### POST /slots/batch
管理员批量创建时段
```
Request:  { "date_from": "2026-08-05", "date_to": "2026-08-11",
            "start_time": "09:00", "end_time": "10:00", "capacity": 5,
            "weekdays": [1,2,3,4,5] }   // 可选，1=周一
Response: { "code": 0, "data": { "created": 5 } }
```

#### PUT /slots/:id
管理员修改时段容量
```
Request:  { "capacity": 8 }
Response: { "code": 0 }
```

#### DELETE /slots/:id
管理员删除时段（仅可删除无预约的时段）
```
Response: { "code": 0 }
```

### 4.3 预约模块

#### POST /reservations
用户预约
```
Request:  { "slot_id": 1 }
Response: { "code": 0, "data": { "id": 10, "status": "pending" } }
```
> 并发控制：使用数据库行级锁 `SELECT ... FOR UPDATE` 扣减名额。

#### DELETE /reservations/:id
用户取消预约
```
Response: { "code": 0 }
```
> 校验：仅 pending 状态、时段未开始时可取消。

#### GET /reservations
查看我的预约
```
Query:    ?status=pending
Response: { "code": 0, "data": [ { "id": 10, "slot": {...}, "status": "pending" } ] }
```

### 4.4 签到模块

#### POST /check-in/:reservation_id
用户签到
```
Response: { "code": 0, "data": { "check_in_time": "2026-08-05T09:05:00Z" } }
```
> 校验：预约为 pending 状态，且当前时间在签到窗口内。

### 4.5 管理端模块

#### GET /admin/reservations
管理员查看所有预约
```
Query:    ?date=2026-08-05&status=pending&page=1&size=20
Response: { "code": 0, "data": { "list": [...], "total": 50 } }
```

#### POST /admin/reservations/:id/cancel
管理员取消预约
```
Response: { "code": 0 }
```

#### POST /admin/reservations/:id/check-in
管理员手动核销签到
```
Response: { "code": 0 }
```

### 4.6 响应码规范

| code | 含义 |
|------|------|
| 0 | 成功 |
| 1001 | 参数错误 |
| 1002 | 未登录/Token 过期 |
| 1003 | 权限不足 |
| 2001 | 时段不存在 |
| 2002 | 时段已满 |
| 2003 | 已预约过此时段 |
| 2004 | 预约不存在 |
| 2005 | 不在签到时间窗口 |
| 2006 | 预约状态不允许此操作 |

## 5. 并发安全设计

预约扣减名额是关键并发场景，采用数据库行锁方案：

```sql
BEGIN TRANSACTION;
  SELECT capacity, reserved FROM time_slots WHERE id = ? FOR UPDATE;
  -- 应用层判断：reserved < capacity
  UPDATE time_slots SET reserved = reserved + 1 WHERE id = ?;
  INSERT INTO reservations (...) VALUES (...);
COMMIT;
```
